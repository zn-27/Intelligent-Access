  ┌──────────┬──────────────────────────────┬───────────────────────────────┐
  │   方面   │       train4.cc (原版)       │    train4_opt.cc (TDMA版)     │
  ├──────────┼──────────────────────────────┼───────────────────────────────┤
  │ 链路技术 │ WiFi (802.11n) + CSMA 有线 + │ 纯 TDMA 无线                  │
  │          │  AdHoc + OpenFlow            │ (simple-wireless-tdma-module) │
  ├──────────┼──────────────────────────────┼───────────────────────────────┤
  │ 交换机   │ OpenFlow 交换机              │ 简单的 IP 转发节点，无控制器  │
  │          │ (ofswitch13)，带控制器节点   │                               │
  ├──────────┼──────────────────────────────┼───────────────────────────────┤
  │          │ 交换机间用 WiFi AdHoc +      │ 所有 16 节点共享一个 TDMA     │
  │ 域间连接 │ VirtualNetDevice 桥接到      │ 信道                          │
  │          │ OpenFlow pipeline            │                               │
  ├──────────┼──────────────────────────────┼───────────────────────────────┤
  │ 路由     │ AODV + OLSR + 静态路由 +     │ 纯静态路由                    │
  │          │ OpenFlow 学习控制器          │ (默认网关指向交换机)          │
  └──────────┴──────────────────────────────┴───────────────────────────────┘

  2. IP 地址方案

  - train4.cc: 每个域独立子网 (10.1.1.0/24, 10.2.1.0/24,
  10.3.1.0/24)，交换机间无线 10.10.1.0/24，需要跨子网路由
  - train4_opt.cc: 全部节点同一子网 10.1.1.0/24，简单扁平拓扑

  3. 复杂度

  - train4.cc (~1137行): 复杂得多，包含 WiFi STA/AP 模式、CSMA 有线、Bridge
  桥接、VirtualNetDevice 包装、ARP 注册、OpenFlow 流表、pcap 抓包、AdHoc
  接口开关等
  - train4_opt.cc (~442行): 大幅简化，所有节点安装 TDMA 设备，通过 SetSlots
  分配时隙，用 IP 转发替代 OpenFlow

  4. TDMA 时隙分配 (train4_opt 独有)

  只有 3 个活跃节点分到了时隙：
  - sw1 (slots 0-3): 4 个时隙做转发
  - sw3 (slot 4): 1 个时隙
  - StaA[1] (slots 5-8): 源节点，4 个时隙
  - StaC[2] (slot 9): 目的节点，1 个时隙
  - 其余节点 0 时隙（静默）

  5. 流量配置

  - train4.cc: 1 条流 (StaA[1]→StaC[2])，2Mbps，第 10 秒启动（等 OpenFlow
  流表建立）
  - train4_opt.cc: 同 1 条流，15Mbps，立即启动（无 OpenFlow 启动延迟）

  总结

  train4_opt 是将 train4 从 WiFi+CSMA+OpenFlow 复杂架构简化为纯 TDMA
  架构的版本。目的是去掉 OpenFlow 控制器和 WiFi CSMA 竞争的不确定性，用 TDMA
  时隙分配来精确控制信道访问，期望获得更稳定和更高的吞吐量。

● 在 train4_opt.cc 中这三个概念的角色完全变了：

  1. Controller — 功能完全不同

  train4_opt 里的 "controller" 是 TdmaControllerHelper，不是 OpenFlow 控制器：

  // 第144-149行：只控制 TDMA 时序参数
  TdmaControllerHelper controller;
  controller.Set("SlotTime", TimeValue(MicroSeconds(500)));
  controller.Set("GuardTime", TimeValue(MicroSeconds(50)));
  controller.Set("DataRate", DataRateValue(DataRate("54Mbps")));

  它只做一件事：管理时隙定时（每个时隙多长、保护间隔多长）。没有任何流表学习、AR
  P 注册、路由决策等 OpenFlow 功能。

  2. Switch (sw1/sw2/sw3) — 退化为普通转发节点

  在 train4.cc 里交换机是 OpenFlow
  交换机，有流表匹配、多端口转发、控制器通信等功能。

  在 train4_opt 里：

  // 第235-243行：只有 sw1 开了 IP 转发，sw2/sw3 根本不转发
  for (uint32_t i = 0; i < allNodes.GetN(); ++i) {
      bool shouldForward = (i == 13); // 只有 sw1
      ipv4->SetAttribute("IpForward", BooleanValue(shouldForward));
  }

  - sw1: 开了 IpForward，收到不属于自己的包会按路由表转发 — 本质就是个普通路由器
  - sw2: 没开转发，0 个时隙 — 完全没用，既不转发也不发送
  - sw3: 没开转发，只有 1 个时隙 — 当前配置下几乎没用

  它们没有 OpenFlow 流表、没有端口学习、没有 pipeline 处理。

  3. 路由协议层 — 完全去掉

  对比：

  ┌─────────────────────┬────────────────┬──────────────────┐
  │                     │   train4.cc    │  train4_opt.cc   │
  ├─────────────────────┼────────────────┼──────────────────┤
  │ AODV                │ 有（动态路由） │ 无               │
  ├─────────────────────┼────────────────┼──────────────────┤
  │ OLSR                │ 有（动态路由） │ 无               │
  ├─────────────────────┼────────────────┼──────────────────┤
  │ OpenFlow 学习控制器 │ 有             │ 无               │
  ├─────────────────────┼────────────────┼──────────────────┤
  │ 静态路由            │ 有             │ 有（仅默认路由） │
  └─────────────────────┴────────────────┴──────────────────┘

  // 第286-293行：域A STA -> sw1 作为网关
  for (uint32_t i = 0; i < StaA.GetN(); ++i) {

  但因为所有节点在同一子网

  总结

  train4_opt 把 train4 的整个 SDN/OpenFlow 架构全部拆掉了，替换成了：
  - TDMA 时分调度 替代 WiFi CSMA 竞争
  - 简单 IP 转发 替代 OpenFlow 交换机
  - 静态默认路由 替代 AODV/OLSR 动态路由

  sw2 目前是个"死节点"（不转发、无时隙），sw3 也基本没发挥作用。只有 sw1

● 关键差异一目了然：

  核心原因：时隙配置不同

  ┌────────────┬─────────────────┬────────────────────────────┐
  │    参数    │  train4_opt.cc  │ train4_opt_tdma_minimal.cc │
  ├────────────┼─────────────────┼────────────────────────────┤
  │ SlotTime   │ 500μs           │ 1100μs                     │
  ├────────────┼─────────────────┼────────────────────────────┤
  │ GuardTime  │ 50μs            │ 100μs                      │
  ├────────────┼─────────────────┼────────────────────────────┤
  │ 总时隙数   │ 16              │ 4                          │
  ├────────────┼─────────────────┼────────────────────────────┤
  │ 每个帧周期 │ 16×550 = 8800μs │ 4×1200 = 4800μs            │
  └────────────┴─────────────────┴────────────────────────────┘

  关键：时隙时长差了 2.2 倍

  minimal 版本的 SlotTime = 1100μs，而 train4_opt 是
  500μs。每帧中每个时隙可以发送的数据量由 SlotTime × DataRate
  决定，但更重要的是：

  没有调用 SetSlots — 默认均分

  minimal 版本完全没有调用 SetSlots，这意味着 4 个节点均分 4 个时隙，每个节点 1
  个时隙。

  而 train4_opt 调用了 SetSlots，给源节点 (StaA[1]) 分了 4 个连续时隙 (slots
  5-8)，给转发节点 sw1 也分了 4 个时隙 (slots 0-3)。

  吞吐量计算

  train4_opt (单跳假设下)：
  - 源节点每帧有 4 个时隙可用
  - 每帧发送时间 = 4 × 500μs = 2000μs
  - 理论吞吐 ≈ 2000μs / 8800μs × 54Mbps ≈ 12.3 Mbps

  minimal 版本：
  - 每个节点只有 1 个时隙
  - 每帧发送时间 = 1 × 1100μs = 1100μs
  - 每帧总时间 = 4 × 1200μs = 4800μs
  - 理论吞吐 ≈ 1100μs / 4800μs × 54Mbps ≈ 12.4 Mbps

  等等，理论上差不多？那还有另一个问题：

  minimal 版本需要多跳转发但没有配置转发

  minimal 有 4 个节点排成一条线 (0 → 1 → 2 → 3)，Node 0 发给 Node 3 需要经过
  Node 1 和 Node 2 两次中继。但是代码里：

  // 没有任何节点开启 IP 转发！
  InternetStackHelper stack;
  stack.Install(nodes);  // 默认 IpForward = false

  没有开 IP 转发，没有配路由。Node 0 的包根本到不了 Node 3（距离 300m，在
  MaxRange=400m 内，但需要 Node 1/2 中继转发，而它们不会转发）。

  所以 minimal 版本的实际吞吐可能极低 — 只有 Node 0 能直接发给 Node 3（都在 400m
   范围内），但如果信号模型不支持那么远，包就全丢了。而 train4_opt 配了 sw1
  做转发，也配了静态路由。

  总结：3 个原因导致 minimal 吞吐更低

  1. SlotTime 太大 (1100μs vs 500μs) — 时隙利用率低
  2. 没有 SetSlots — 均分时隙而非集中分配给活跃流
  3. 没配路由/转发 — 需要多跳但中间节点不转发，大量丢包

❯ 增加时隙总数并用 SetSlots 集中分配给活跃节点，这里的改动是什么意思            

● SetSlots 的工作原理

  TDMA 的核心是把时间切成帧，每帧分成若干时隙，每个时隙只能有一个节点发送。

  默认行为（不调用 SetSlots）

  4个节点, 4个时隙, 均分:
  帧: [Node0发 | Node1发 | Node2发 | Node3发]
       ─────────────────────────────────────────
       每个节点占 1/4 = 25% 时间

  Node 0 是源节点，它只在第 1 个时隙能发数据，其余 3/4 的时间空等。而 Node
  1、Node 2 根本没有数据要发，它们的时隙白白浪费了。

  调用 SetSlots 之后

  tdma.SetSlots(8,
      0, 1,1,1,1, 0,0,0,0,  // Node 0: 占时隙 0,1,2,3
      1, 0,0,0,0, 0,0,0,0,  // Node 1: 不占时隙
      2, 0,0,0,0, 0,0,0,0,  // Node 2: 不占时隙
      3, 0,0,0,0, 1,0,0,0   // Node 3: 占时隙 4
  );

  每个参数行的格式是：nodeId, slot0, slot1, slot2, ..., slot7

  - 1 表示该时隙分配给这个节点
  - 0 表示该时隙不分配给这个节点

  对应的时间线：

  8个时隙的帧:
  帧: [Node0 | Node0 | Node0 | Node0 | Node3 | 空 | 空 | 空]
       ────────────────────────────────────────────────────────
       Node 0 占 4/8 = 50% 时间
       Node 3 占 1/8 = 12.5% 时间（接收确认等）
       空      占 3/8（预留给未来扩展）

  为什么这样能提高吞吐

  场景：Node 0 往 Node 3 发 15Mbps 的 UDP 流。

  - 均分时隙：Node 0 每帧只有 1 个时隙发数据，最大可用带宽 = 54Mbps × 1/4 =
  13.5Mbps，加之时隙大 (1100μs) 开销高，实际更低，可能只有几 Mbps。
  - 集中分配：Node 0 每帧有 4 个时隙发数据，最大可用带宽 = 54Mbps × 4/8 =
  27Mbps，且时隙小 (500μs)，轻松承载 15Mbps 的流量。

  简单说就是：把闲着节点的时隙挪给忙的节点用，让源节点在单位时间内能发更多数据。

● TDMA 在协议栈中的位置

  simple-wireless-tdma 模块是一个**MAC 层（数据链路层子层）**协议。它替代的是
  WiFi 的 MAC (CSMA/CA) 或 CSMA 的 MAC，不涉及网络层及以上。

  OSI 层次        train4.cc (原版)              train4_opt (TDMA版)
  ─────────────────────────────────────────────────────────────
  应用层          UDP OnOff/Sink                 UDP OnOff/Sink
  传输层          UDP                            UDP
  网络层          IP + AODV/OLSR + 静态路由       IP + 静态路由
                  + OpenFlow 控制器               （没有路由协议）
  ────── MAC层 ────── WiFi MAC (CSMA/CA)          TDMA MAC (时分复用)
  物理层          WiFi PHY (802.11n)             SimpleWireless PHY

  能否在上面跑其他路由协议？

  可以。 TDMA 只管 MAC
  层的"谁在什么时间发"，跟网络层的路由决策完全无关。你可以在 TDMA 之上叠加：

  ┌──────────┬────────┬────────────────────────────────────┐
  │ 路由协议 │ 可行性 │                说明                │
  ├──────────┼────────┼────────────────────────────────────┤
  │ AODV     │ 可以   │ 按需路由，适合拓扑变化场景         │
  ├──────────┼────────┼────────────────────────────────────┤
  │ OLSR     │ 可以   │ 先验式路由，适合节点较多的稳定拓扑 │
  ├──────────┼────────┼────────────────────────────────────┤
  │ 静态路由 │ 可以   │ 你目前 train4_opt 的方案           │
  ├──────────┼────────┼────────────────────────────────────┤
  │ 全局路由 │ 可以   │ ns-3 内置，适合静态拓扑            │
  └──────────┴────────┴────────────────────────────────────┘

  代码上只需要换协议栈：

  // 当前 train4_opt 的写法（纯静态路由）
  InternetStackHelper stack;
  stack.Install(allNodes);

  // 改成 AODV + 静态路由
  Ipv4ListRoutingHelper list;
  list.Add(AodvHelper(), 10);
  list.Add(Ipv4StaticRoutingHelper(), 100);
  InternetStackHelper stack;
  stack.SetRoutingHelper(list);
  stack.Install(allNodes);

  MAC 层的 TDMA 配置完全不用动。

  能否叠加 SDN/OpenFlow？

  理论上可以，但需要额外工作。 核心问题是 ofswitch13 模块依赖 CSMA 或 
  Point-to-Point 类型的 NetDevice（它需要 Ethernet 帧），而 TDMA 模块提供的是
  SimpleWirelessNetDevice。

  有两条路：

  方案 A：用 VirtualNetDevice 桥接（类似 train4.cc 的做法）

  train4.cc 里已经用了这个技巧 — 用 VirtualNetDevice 包装 WiFi 设备给 OpenFlow
  用。同理可以包装 TDMA 设备：

  TDMA设备收到包 → 注入到 VirtualNetDevice → OpenFlow Pipeline 处理
  OpenFlow 发包 → VirtualNetDevice.SendCallback → 通过 TDMA 设备发出

  但需要手动处理帧格式转换（TDMA 传的是 IP 包，OpenFlow 需要 Ethernet
  帧），train4.cc 的 WifiToVirtualDevForward 函数做的就是这件事。

  方案 B：修改 TDMA 模块让它直接支持 Ethernet 帧

  改动量大，不推荐。

  总结

  TDMA 是 MAC 层协议，只管信道接入
            ↓ 不影响
  网络层：可以换 AODV/OLSR/OSPF/静态路由，随便组合
            ↓ 也可以加
  SDN/OpenFlow：可以，但需要 VirtualNetDevice 桥接 + 帧格式转换

  如果你想在 TDMA 基础上试 SDN，最直接的方式是在 train4_opt.cc 里加入 train4.cc
  的 VirtualNetDevice + OpenFlow 那套逻辑，把 TDMA 设备当底层传输来用。

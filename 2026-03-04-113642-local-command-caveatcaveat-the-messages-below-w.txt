  // 修改后：先添加Ethernet头再传递
  bool WifiToVirtualDevForward(Ptr<VirtualNetDevice> vdev, Ptr<NetDevice> dev,
                               Ptr<const Packet> packet, uint16_t protocol,
                               const Address &source, const Address &dest,
                               NetDevice::PacketType packetType)
  {
      // ... 检测ICMP代码 ...

      // 【关键修复】为IP包添加Ethernet头
      Ptr<Packet> packetCopy = packet->Copy();
      Mac48Address srcMac = Mac48Address::ConvertFrom(dev->GetAddress());
      Mac48Address dstMac = Mac48Address::ConvertFrom(vdev->GetAddress());

      EthernetHeader ethHeader(false); // 不使用preamble
      ethHeader.SetSource(srcMac);
      ethHeader.SetDestination(dstMac);
      ethHeader.SetLengthType(0x0800); // IPv4

      EthernetTrailer ethTrailer;
      packetCopy->AddHeader(ethHeader);
      packetCopy->AddTrailer(ethTrailer);

      // 调用 vdev->Receive()
      bool ret = vdev->Receive(packetCopy, 0x0800, srcMac, dstMac, packetType);
      return ret;
  }

● 根据运行结果，我来分析丢包率高的原因：

  流量统计结果分析

  ┌───────┬─────────────────────────────────────────┬────────┬───────┐
  │ Flow  │                  路径                   │ 丢包率 │ 延迟  │
  ├───────┼─────────────────────────────────────────┼────────┼───────┤
  │ Flow0 │ StaA[1] (10.1.1.2) → StaC[2] (10.3.1.3) │ 51.64% │ 469ms │
  ├───────┼─────────────────────────────────────────┼────────┼───────┤
  │ Flow1 │ StaA[3] (10.1.1.4) → StaB[1] (10.2.1.2) │ 26.09% │ 481ms │
  ├───────┼─────────────────────────────────────────┼────────┼───────┤
  │ Flow2 │ StaB[0] (10.2.1.1) → StaC[1] (10.3.1.2) │ 26.91% │ 454ms │
  ├───────┼─────────────────────────────────────────┼────────┼───────┤
  │ Flow3 │ StaC[0] (10.3.1.4) → StaC[2] (10.3.1.6) │ 0%     │ 1.6ms │
  └───────┴─────────────────────────────────────────┴────────┴───────┘

  关键发现

  1. 域内流量无丢包，跨域流量丢包严重

  - Flow3是C域内部流量，丢包率0%，说明WiFi网络本身没问题
  - 问题出在跨域转发路径上

  2. 11.5秒的CDL操作是主要原因

  [ApProtocolInfoApp] STA 00:00:00:00:00:17 AdHoc interface UP (ifIndex=2)
  [ApProtocolInfoApp] STA 00:00:00:00:00:18 AdHoc interface UP (ifIndex=2)
  [ApProtocolInfoApp] STA 00:00:00:00:00:19 AdHoc interface UP (ifIndex=2)

  11.5秒时CDL被调用，导致C域STA的AdHoc接口被启用。这会：
  - 修改路由表优先级
  - 可能导致路由震荡
  - 干扰正常的跨域转发

  3. Flow0 (A→C) 丢包率最高 (51.64%) 的原因

  Flow0的路径最复杂：
  StaA[1] (10.1.1.2)
    → ApA (10.1.1.5/10.1.1.6)
    → sw1
    → sw3 (WiFi AdHoc)
    → ApC (10.3.1.7)
    → StaC[2] (10.3.1.3)

  问题：
  1. 经过两个交换机 (sw1 → sw3)，每跳都可能丢包
  2. C域目的STA有两个接口：WiFi接口(10.3.1.3) + AdHoc接口(10.3.1.6)
  3. 11.5秒后AdHoc接口启用，可能导致路由混乱，数据包发往错误接口

  4. 为什么Flow3没有丢包？

  Flow3是C域内部流量 (10.3.1.4 → 10.3.1.6)，路径：
  - 直接通过C域的WiFi网络
  - 不经过交换机
  - 不受CDL操作影响（或者说两个接口都在同一节点）

  丢包原因总结

  1. CDL组网模式切换 (11.5秒) 破坏了已建立的跨域流表规则
  2. 多跳转发：跨域流量需要经过多个交换机，每跳都有丢失风险
  3. 路由竞争：C域STA同时有WiFi和AdHoc两个接口，CDL启用AdHoc后可能导致路由表混乱
  4. 流表超时：idle=30秒，hard=60秒的流表规则可能在CDL操作后失效

  解决方案建议

  1. 禁用CDL操作（已经做了部分，1152行的SetPriorityToAll仍被注释）
  2. 调整流表超时时间：增加idle和hard timeout
  3. 为跨域流量添加更高优先级的流表规则
